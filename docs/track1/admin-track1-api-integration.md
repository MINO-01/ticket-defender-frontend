# 관리자 공연 선택 및 Track 1 실제 API 연동 (Frontend Issue #20)

이 문서는 관리자 Track 1 화면이 실제 Spring API와 연결된 범위, 화면에서 표시하지 않는 정보, 후속 작업을 정리합니다.
기준 계약은 Backend main의 `docs/api/admin-events-v1.yaml`, `docs/api/admin-events-v1.md`, `docs/api/track1-admin-evidence-read-v1.md`입니다.

## 연동 범위

| 화면 | 주소 | 호출 API |
| --- | --- | --- |
| 공연 선택 | `/app/analysis/findings?eventId=` | `GET /api/v1/admin/events?page=&pageSize=100` |
| 군집 목록 | `/app/analysis/findings?eventId=&page=&sort=` | `GET /api/v1/admin/track1/clusters?eventId=&page=&pageSize=20&sort=` |
| 군집 상세 | `/app/analysis/findings/detail?eventId=&analysisRequestId=&clusterId=` | `GET /api/v1/admin/track1/clusters/detail?eventId=&analysisRequestId=&clusterId=` |

- 모든 요청은 기존 Keycloak 세션의 관리자 JWT와 공통 `adminApiClient`를 사용합니다. tenantId와 역할은 요청에 보내지 않고 화면에서 권한 근거로 쓰지 않습니다.
- 응답은 Zod 스키마로 검증합니다. 응답의 공연 ID, 페이지, 군집 식별자가 요청과 다르면 계약 불일치로 처리합니다.
- 분석 요청 ID와 군집 ID에는 슬래시가 포함될 수 있어 경로가 아닌 쿼리 값으로 인코딩해 전달합니다.

## 공연 선택

- 서버가 반환한 공연의 내부 UUID(`items[].id`)만 선택값으로 사용합니다. `externalEventId`는 고객사 간에 같을 수 있어 식별자로 쓰지 않습니다.
- 공연은 서버 페이지(100개) 단위로 불러오며 `공연 더 불러오기`로 다음 페이지를 이어 붙입니다.
- 선택 상태는 주소의 `eventId` 쿼리로 유지합니다. 주소로 접근하면 접근 가능 공연 목록에서 해당 공연을 다시 확인하며, 첫 페이지에 없으면 최대 10페이지까지 이어서 조회합니다. 확인되기 전에는 Track 1 API를 호출하지 않습니다.
- 군집 상세 주소도 접근 가능 공연 목록에서 공연을 먼저 확인한 뒤에만 상세 API를 호출합니다. 공연 목록이 409, 403, 장애이거나 목록에 없는 공연이면 상세를 조회하지 않습니다.
- 공연을 바꾸면 페이지 값을 버리고 이전 요청을 중단합니다. 늦게 도착한 이전 응답은 요청 경로가 현재와 달라 표시되지 않습니다.
- `AdminEventGate`와 `useSelectedEventId`는 Track 2와 Case 화면에서도 재사용할 수 있게 분리했습니다. 이번 Issue에서는 해당 화면에 연결하지 않았습니다.

## 표시 원칙

- Risk Score는 0~1 사이 조사 우선순위 신호로 소수 둘째 자리까지 표시합니다. 백분율이나 부정 거래 확률로 표시하지 않습니다. 값이 없으면 0점이 아니라 `값 없음`으로 표시합니다.
- 응답의 `coverage`는 `STORED_EVIDENCE_ONLY`만 허용합니다. 저장 구성원은 중복 저장 방지로 일부 누락될 수 있어 전체 분석 스냅샷이나 확정 판정으로 안내하지 않습니다.
- 목록이 0건이면 "저장된 군집이 없습니다"로 표시하고, 분석 실행 여부나 실패 여부를 뜻하지 않는다고 안내합니다.
- 검색과 연결 정보 필터는 Backend가 지원하지 않아 실제 연동 화면에서 제공하지 않습니다. 정렬은 서버 정렬 값(`priority-desc`, `priority-asc`, `recent`)만 사용합니다.

## 오류 구분

| 결과 | 화면 안내 |
| --- | --- |
| 401 | 세션을 정리하고 기존 재로그인 화면으로 전환 |
| 403 | 필요한 역할 없음 |
| 404 | 존재하지 않거나 접근 범위 밖 (두 경우를 구분하지 않음) |
| 409 `TENANT_SELECTION_REQUIRED` | 여러 고객사 소속 계정 미지원 (DEC-02 PENDING) |
| 400 | 요청 값 오류 |
| 500 / 503 | 서버 오류 / 일시 장애 (DB 장애 시 공연 목록은 503, Track 1은 500) |
| 네트워크 실패 | 서버 연결 실패 |
| 스키마 불일치 | 응답 형식이 계약과 다름 |

모든 실패는 빈 목록, 0점, 합성 데모 데이터로 대체하지 않으며 재시도 버튼을 제공합니다. 서버의 상세 메시지는 표시하지 않고 고정 문구만 사용합니다.

## 데모 데이터 분리

- 인증 세션에서는 실제 API 화면만 엽니다. 기존 합성 데모 화면과 그래프는 개발 빌드의 `VITE_ADMIN_DEMO_PREVIEW=true` 미리보기에서만 열립니다.
- 인증 세션에서 기존 데모 주소(`/app/analysis/findings/DEMO-CL-001` 등)에 접근하면 주소 오류로 안내하고 API를 호출하지 않습니다.
- 데모 화면과 그래프 라이브러리는 미리보기에서만 지연 로드해 인증 세션의 화면 번들에 포함하지 않습니다.

## 미지원 항목

현재 Backend 응답은 공연 정보, 분석 메타데이터, 저장 구성원(`auditId`, `accountId`, `reservationNo`)만 제공합니다.
다음 정보가 없으므로 실제 상세 화면에서는 관계 그래프를 그리지 않고 미지원 사유를 표시합니다.

- 공유 신호 종류와 설명
- 신호별 계정 연결 관계와 그래프 간선
- 좌석 정보

## 후속 Backend 작업 제안

완전한 관계 그래프 화면에는 별도 Backend Issue가 필요합니다.

1. 분석 응답의 신호별 연결 관계(신호 종류, 연결된 구성원, 근거 설명)를 고객사와 공연 범위로 저장하는 영속 구조와 migration
2. 원문 결제, 주소, 기기, IP 값 대신 고객사 범위 HMAC 토큰 또는 신호 종류만 노출하는 응답 계약과 개인정보 검토
3. 상세 API의 `coverage`에 그래프 제공 범위를 구분하는 값 추가와 Frontend 스키마 갱신
4. 저장 구성원 누락 여부를 화면에서 구분할 수 있는 분석 응답 구성원 수 등 메타데이터

## 로그인 후 주소 복원

기존 인증 정책상 액세스 토큰은 메모리에만 있어 새로고침하면 다시 로그인해야 하고, Keycloak은 등록된 고정 콜백 주소(`/app/overview`)로 돌아옵니다.
로그인 버튼을 누를 때 현재 관리자 경로와 쿼리만 현재 탭의 `sessionStorage`에 보관했다가 인증이 완료되면 한 번만 복원하고 지웁니다.

- Redirect URI와 PKCE, 콜백 처리 방식은 바꾸지 않습니다. 토큰, 인증 코드, fragment는 저장하지 않습니다.
- 동일 출처의 `/app` 하위 경로만 복원합니다. 다른 출처, 공개 팬 화면, 경로 이탈(`..`, `%2e%2e`), 역슬래시, fragment, 제어 문자가 있는 값과 10분이 지난 값은 버립니다.
- 로그인에 실패하면 이동하지 않습니다. 복원한 주소의 공연과 군집은 각 화면이 서버 권한을 다시 확인합니다.

## 실제 연동 검증

모든 실행은 격리 Keycloak(HTTPS, 테스트 CA), 격리 MySQL 8.0 컨테이너, 합성 데이터로 수행했습니다. 실제 고객사 데이터와 운영 환경이 아닙니다.
환경 구성 방식은 `docs/keycloak/README.md`와 같으며, 비밀번호, 인증서 개인키, 토큰과 실행 스크립트는 저장소 밖에 두었습니다.

| 실행 | Backend main | 실제 HTTP (Keycloak 토큰, Vite 프록시, Spring, MySQL) | 실제 브라우저 (Chrome, Keycloak 로그인 화면) |
| --- | --- | --- | --- |
| 1차 (2026-11-01) | `d932a31` | 31건 중 29건 통과 (아래 Backend 확인 사항 2건 실패) | 15건 통과 |
| 재검증 (2026-11-02) | `7c772ac` (#58, #59 반영) | 31건 통과 | 15건 통과 |
| Backend #58 추가 보안 검증 (2026-11-02) | `7c772ac` | 12건 통과 (관리자 업무 API 36개 경로 모두 409) | 해당 없음 |

- 확인한 동작: 접근 가능 공연만 반환, 미부여 공연과 타 고객사 공연 404, 역할 없음 403, 다중 고객사 409, 토큰 없음, 잘못된 issuer, 잘못된 audience, 서명 변조, 만료 토큰 401, Track 1 서버 페이지와 정렬, 저장 증거와 응답 일치, 같은 군집 ID를 가진 타 고객사 증거 비노출, 로그인 전 상세 주소 복원, 공연 변경 시 이전 요청 중단, DB 장애 시 오류 안내와 복구 후 재시도, 로그아웃 후 차단, 브라우저 저장소와 로그의 JWT 부재
- #58 추가 검증: 비활성 멤버십과 비활성 고객사는 다중 소속 판단에서 제외, 다중 고객사 계정의 업무 API 409와 ProblemDetail 5개 필드(`title`, `status`, `instance`, `code`, `requestId`)만 응답, 차단 중 승인과 증거와 보고서와 PDF 발급 상태 불변, `tenantId` 쿼리와 `X-Tenant-Id` 헤더로 우회 불가, 권한 없는 공연과 없는 자원은 409가 아닌 404 유지
- Spring은 만료 시각 이후 기본 60초의 시계 오차를 허용합니다. Frontend는 만료 30초 전에 토큰을 폐기하므로 이 구간의 토큰을 보내지 않습니다.
- 실제 HTTP와 브라우저 결과는 위 실행 시점의 기록입니다. 이후 추가한 화면 오류 상태 테스트는 아래 컴포넌트 테스트이며 실제 HTTP로 다시 실행하지 않았습니다.

### 재현 조건

E2E 스크립트는 저장소에 포함하지 않았습니다. 같은 결과를 재현하려면 다음 조건이 필요합니다.

- Keycloak: `ticket-defender-demo` realm을 HTTPS와 테스트 CA로 실행하고, 관리자 client(`ticket-defender-admin` audience)와 E2E 전용 password grant client를 둡니다. 합성 사용자는 고객사 관리자, 분석가, 역할 없는 멤버십, 멤버십 없음, 두 고객사 소속 계정 5종입니다.
- MySQL 8.0: 격리 컨테이너에 Backend migration을 적용하고 합성 고객사 2곳, 공연(접근 가능 2개, 미부여 1개, 타 고객사 1개), 멤버십과 역할, 같은 군집 ID를 포함한 고객사별 Track 1 저장 증거를 넣습니다. 실제 개인정보는 쓰지 않습니다.
- Spring: Backend main jar를 `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `TICKET_DEFENDER_SECURITY_ADMIN_ISSUER`, `TICKET_DEFENDER_SECURITY_ADMIN_AUDIENCE`, `TICKET_DEFENDER_SECURITY_ADMIN_JWK_SET_URI` 환경변수와 테스트 CA truststore로 실행합니다. 값은 실행 환경에만 둡니다.
- Frontend: `VITE_ADMIN_AUTH_PROVIDER`, `VITE_ADMIN_AUTH_ISSUER`, `VITE_ADMIN_AUTH_CLIENT_ID`, `VITE_ADMIN_AUTH_AUDIENCE` 환경변수로 Vite 개발 서버를 실행하고 Vite 프록시로 Spring에 연결합니다.
- DB 장애: 격리 MySQL 컨테이너를 일시 정지(`docker pause`)한 뒤 오류 화면을 확인하고, 재개 후 다시 시도로 복구를 확인합니다. 공유 DB나 운영 DB에는 적용하지 않습니다.
- 결과 기록에는 토큰, 비밀번호, 인증 코드를 남기지 않고 통과 여부와 상태 코드만 남깁니다.

## 화면 오류 상태 컴포넌트 테스트

`src/test/admin-track1-api.test.tsx`는 Mock 인증 어댑터와 fetch로 다음을 검증합니다. 실제 HTTP 검증을 대체하지 않습니다.
오류 응답은 Backend main `7c772ac`의 ProblemDetail 형식을 따르며, 응답에 내부 메시지가 섞여 와도 화면에 노출하지 않는지 함께 확인합니다.

| 항목 | 검증 내용 |
| --- | --- |
| 403 | 공연 목록, 군집 목록, 상세에서 역할 없음 안내 |
| 404 | 군집 목록과 상세에서 존재하지 않거나 범위 밖 안내 (두 경우 구분 안 함) |
| 409 | 공연 목록, 군집 목록, 공연 확인 이후 상세 API에서 다중 고객사 미지원 안내, 구성원 비표시 |
| 503 | 공연 목록 장애 안내, 빈 목록이나 데모 데이터로 대체하지 않음, 장애 중 Track 1 미호출 |
| Track 1 DB 장애 | 실제 계약인 Spring 기본 500 본문을 서버 오류로 표시. 503은 현재 Track 1 계약이 아니며 방어적으로만 확인 |
| 복구 | 공연 목록 503, 군집 목록 장애, 상세 장애, 상세 주소의 공연 확인 503 이후 다시 시도로 같은 요청 재조회 |
| 정합성 | 공연 전환 시 이전 오류와 늦은 응답 미표시, 새로고침 시 주소의 `page`와 `sort`로 같은 서버 페이지 재조회 |
| 데모 분리 | 인증 세션에서 데모 데이터와 데모 상세 경로 미사용 |

## Backend 확인 사항 (해결)

1. **다중 고객사 계정의 Track 1 직접 조회**: Backend #58(main `7c772ac`)에서 해결했습니다. Track 1 목록과 상세를 포함한 관리자 업무 API가 다중 고객사 계정을 409 `TENANT_SELECTION_REQUIRED`로 차단하며, 재검증에서 Track 1 직접 조회가 200에서 409로 바뀐 것을 확인했습니다. DEC-02 확정 전 임시 정책이며 고객사 선택 기능은 아닙니다. Frontend의 상세 주소 공연 확인은 그대로 유지합니다.
2. **DB 연결 실패 시 공연 목록 500**: Backend #59(main `7c772ac`)에서 해결했습니다. 트랜잭션 시작 단계의 DB 연결 획득 실패도 503 `DEPENDENCY_UNAVAILABLE`로 응답하며, 재검증에서 공연 목록이 500에서 503으로 바뀐 것을 확인했습니다.

## 남은 검증 한계

- **Track 1 DB 장애 500**: Track 1 군집 API는 #59 처리기 범위 밖이라 DB 장애 시 Spring 기본 500 본문을 반환합니다. Frontend는 서버 오류로 표시하고 빈 목록으로 바꾸지 않지만, 공연 목록과 같은 503 계약 적용 여부는 Backend 결정이 필요합니다.
- **Track 1 비UUID 분석 결과의 Case 연결**: Case 생성은 UUID 형식 `analysisRequestId`만 받습니다. 기존 비UUID 레거시 Track 1 분석 결과를 Case에 연결할 방식은 정해지지 않았습니다.
- **공식 PDF 전체 흐름**: 실제 PDF 생성, 발급, 다운로드 전체 E2E는 검증하지 않았습니다.
- **운영 DB 마이그레이션**: 검증은 격리 MySQL 컨테이너에서만 수행했으며 공식 운영 환경의 migration 적용은 검증하지 않았습니다.
- **합성 격리 환경**: 이번 E2E는 합성 데이터와 격리 환경 결과이며 운영 준비 완료를 뜻하지 않습니다.
- **E2E 자동화**: 실제 HTTP와 브라우저 E2E 스크립트는 저장소 밖에서 수동 실행했습니다. 환경변수 기반으로 재현 가능한 E2E 자동화는 별도 Issue가 필요합니다.
